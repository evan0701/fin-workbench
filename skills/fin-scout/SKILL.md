# fin-scout · 元技能（发现者）

fin-workbench 飞轮的发生器：**发现重复 → 判定价值 → 移交铸造**。

> 分工：fin-scout 管"该不该铸"，fill-forge 管"怎么铸"，映射助手管"新数据源接入"。
> 本技能只判定和移交，不亲自铸造、不亲自填表。

## 核心机制：观察台账

台账文件固定在 `skills/fin-scout/scout-log.md`（本技能目录下，只增不删）。

### 何时记一笔

满足任一条件即记录"观察中"：

1. 用户描述的动作带有明确的**周期性信号**："每个月""每季度""每次报""又要填了""月底那件事"
2. 动作符合 **四段模式**：固定源文件 → 固定取数 → 固定加工 → 固定产物
3. 用户直接问"这个能不能做成技能"

### 台账条目格式

```markdown
| 日期 | 动作一句话 | 四段模式（源→取数→加工→产物） | 频次信号 | 状态 | 结论 |
```

状态机：`观察中 → 建议铸造 → 已铸造(链接) / 不铸(原因) / 观察中(继续)`。

**铁律：只增不删。** 误报不删行，改状态为"不铸"并写原因 —— 误报原因就是判定清单的校准数据。

## 判定清单（建议铸造前逐条过，全"是"才建议）

| # | 问题 | 为什么 |
|---|---|---|
| 1 | 频次 ≥ 每月一次（或每季 ≥1 且下次还会做）？ | 一次性动作不值得铸造（见排除项） |
| 2 | 四段模式稳定？源文件格式、取数逻辑、产物结构基本不变？ | 模式漂移的活不适合固化 |
| 3 | 数据源可以程序化读取（Excel/CSV/网页下载文件）？ | 需要人脑判断的输入没法自动化 |
| 4 | 口径可以写清楚（每个数从哪来、怎么算）？ | 口径写不清 = 铸出来也过不了回填考试 |
| 5 | 产物有固定的复核需求？ | 有复核点的表才需要"成品+复核清单"结构 |

### 排除项（直接"不铸"）

- 一次性的专项（年度审计配合、临时专项报表）
- 每次内容差异极大、只共享"表格式"的动作
- 用户明确说"这次特殊处理"
- 频次低且下次做时业务规则大概率已变

## 建议铸造的话术（触发时对用户说）

> 这个动作我已经观察到你做了 N 次（日期列表），四段模式稳定、口径可固化，
> 符合铸造标准。建议移交 fill-forge 铸造成技能：
> 铸成后每月从"手工 N 分钟"变成"拖入导出文件 → 成品 + 复核清单"。
> 要开始的话，请准备三样材料：目标表模板、数据源导出、上期人工成品。

用户同意 → 检查材料 → **移交 fill-forge**（把台账条目链接一并交给它）。
材料不全 → 按缺什么列清单，等用户补齐，台账状态保持"建议铸造"。

## 与总入口的关系

`skills/fin-workbench/SKILL.md` 的路由表把"我每个月都要做 X"类请求先路由到这里；
本技能判定通过后转发 `skills/fill-forge/SKILL.md`。维护者新增路由时保持这个顺序不变。

## 维护者职责

- 每月末扫一遍台账：把"观察中"但已 ≥3 次的条目主动向用户提出铸造建议
- 新的排除项/误报模式回写到 `references/识别启发.md`（只增不减）
